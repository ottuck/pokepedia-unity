## 요약

- Pokepedia의 **퀴즈(Quiz) → 띠부띠부씰 컬렉션(Collection) → Unity 배틀(Battle)** 루프를 소규모로 완성한다.
- 퀴즈로 모은 포켓몬 중 **배틀을 지원하는 6마리**로 NPC와 **1:1 턴제 배틀**을 한다. 151마리 지원은 필수가 아니다.
- 연출은 **Showcase**(피카츄·거북왕, 고급 연출)와 **Standard**(나머지 4마리, 공통 연출) 두 등급이며 **엔진은 하나**다.
- Unity 6.3 LTS, C#, uGUI, 순수 C# 엔진, 블랙·화이트 애니메이션 스프라이트, 현대 포켓몬 데이터(18타입·능력치 6종) 기반의 단순화 규칙(명중·급소 포함).
- 퀴즈를 Unity로 다시 만들지 않는다. 기존 Pokepedia DB는 변경하지 않는다.

## 1. 프로젝트 개요

### 목표

Pokepedia에서 모은 띠부띠부씰 포켓몬 중 배틀 지원 포켓몬으로 NPC와 싸우는 **Unity + C# 기반 2D 턴제 배틀 게임**을 만든다.

- 게임보이 감성의 레트로 UI를 유지한다.
- 웹(WebGL)으로 배포하고, Pokepedia에서 **iframe으로 접근**한다. 포트폴리오 허브에서는 단독으로도 플레이할 수 있다.
- 기존 Pokepedia의 퀴즈·도감·컬렉션·랭킹은 그대로 유지한다.
- **모바일 앱은 출시하지 않지만, 모바일 브라우저에서 화면이 완벽하게 보이는 것이 목표다** [확정].
- 대규모 포켓몬 게임이 아니라 **제대로 설계하고 연출한 소규모 Unity 게임 포트폴리오**다.

### 개발 목적

- C#을 실전 프로젝트로 학습 (Java 경험 활용)
- BattleEngine, DamageCalculator, 타입 상성, NPC AI, 상태 설계 등 **도메인 설계 경험**
- Unity 2D, uGUI, Animator, Particle System, Shader, 오디오, WebGL 배포 경험
- 규칙(엔진)과 콘텐츠(데이터·에셋·텍스트)의 분리 설계
- **Unity를 폭넓게 경험:** 월드/UI 렌더링 분리, Light2D, 후처리, Shader Graph, VFX, 카메라 연출까지 "Unity를 제대로 써 봤다"고 말할 수 있는 범위를 넓힌다. 이 목적은 용량·작업량보다 우선한다 [확정, 2026-10-17].
- 대규모 서비스·사용자 확보·상업화가 목적이 아니다. 학습과 완성도 우선.

### 프로젝트 완료 기준 [확정]

다음 네 가지를 달성하면 성공이다. (포켓몬 수는 기준이 아니다.)

1. 순수 C#으로 게임 규칙을 작성하고 자동화 테스트할 수 있다.
2. Unity에서 UI·애니메이션·사운드·이펙트를 직접 구현해 봤다.
3. 브라우저에서 플레이 가능한 완성형 미니게임을 공개했다.
4. 다른 개발자에게 게임 아키텍처와 설계 의도를 설명할 수 있다.

## 3. 최종 게임 루프 [확정]

```text
Pokepedia 퀴즈 (React, 기존)
   ↓ 이름 맞히기 정답
띠부띠부씰 컬렉션 (기존, Supabase user_sticker)
   ↓ 보유 포켓몬 목록을 한 번 전달 (React → Unity)
Unity Battle (신규)
   보유 포켓몬 ∩ 배틀 지원 포켓몬 선택 → NPC와 1:1 전투 → 결과 표시
```

- 퀴즈는 **스티커를 모으는 콘텐츠**, 배틀은 **모은 포켓몬 중 일부를 쓰는 추가 콘텐츠**다.
- 연결은 **단방향**(React → Unity). 배틀 결과로 스티커·랭킹을 갱신하지 않는다.
- 퀴즈에서 **배틀 지원 포켓몬이 처음에 등장**하도록 수정한다 (9.7, 게임 완성 후).
- 진입점: Pokepedia **별도 "배틀" 메뉴**(내비게이션). 퀴즈 보상 화면의 배틀 안내는 게임 완성 후 결정한다.

## 5. 게임 범위

### 5.1 지원 포켓몬 로스터 [확정]

Pokepedia가 151마리를 지원한다고 해서 Unity 배틀도 151마리를 지원할 이유는 없다. 지원 범위를 제한해 완성도를 높인다.

| 등급 | 포켓몬 | 타입 | 연출 |
|---|---|---|---|
| **Showcase** | 피카츄 #025 | 전기 | 전기 파티클, 공격 준비·발동, 전용 피격 모션 |
| | 거북왕 #009 | 물 | 물대포 이펙트, 충격·넉백, 묵직한 움직임 |
| **Standard** | 리자몽 | 불꽃/비행 | 공통 애니메이션 + 타입별 간단한 이펙트 |
| | 이상해꽃 | 풀/독 | 〃 |
| | 팬텀 | 고스트/독 | 〃 |
| | 뮤츠 | 에스퍼 | 〃 (전설, 드물게 등장, 6.5) |

- 총 6마리. 출시 순서는 Showcase → Standard이며, 첫 릴리스는 2~4마리만 있어도 충분하다.
- **공개 범위 [확정, 2026-10-17 사용자 결정]:** Showcase 2마리(피카츄·거북왕)로 **하나의 흐름을 먼저 완성**한다(Pokepedia 퀴즈 → 띠부씰 → 배틀). Standard 4마리는 데이터로 남겨 두고 연출·공개는 "이후 확장"으로 미룬다(에셋·연출 반복 작업이 크고, 엔진이 로스터 수를 모른다는 설계는 6종 데이터와 테스트로 이미 보였다).
- 필요한 이펙트·기술의 종류는 로스터의 타입으로 결정된다. 타입이 겹치게 골라 작업량을 통제했다.
- 이후 추가는 **로스터에 항목을 늘리는 것**(데이터 + 스프라이트 + 필요 시 연출 오버라이드)으로 한다. **엔진은 지원 포켓몬 수를 몰라야 한다.**
- 18타입 상성 시스템은 C#으로 전부 구현하되 **실제 기술·이펙트는 로스터가 쓰는 타입만** 만든다.
- 포트폴리오·README에는 **전체 151마리 중 일부만 배틀을 지원한다는 사실을 명확히 표시**한다.

### 5.2 품질 등급: Showcase / Standard [확정]

엔진은 하나이고 **시각적 표현만 다르게** 적용한다. Showcase도 가짜 로직이 아니라 **실제 엔진을 쓰는 플레이 가능한 콘텐츠**여야 한다.

| 연출 요소 | Standard | Showcase |
|---|---|---|
| 등장 | 페이드 인 | 포켓몬 전용 등장 연출 |
| 공격 | 짧게 앞으로 이동 (접촉형/발사형/효과형 공통 타임라인) | 준비 동작 + 공격 애니메이션 |
| 기술 효과 | 타입별 공통 이펙트 | 커스텀 파티클·셰이더 |
| 피격 | 흔들림 + 깜빡임 | 충격·넉백·카메라 효과 |
| 급소 / 빗나감 | 공통 문구 + 효과음 | 전용 연출 (화면 번쩍임, 회피 모션) |
| 승리 | 결과 메시지 | 전용 승리 연출 |
| 사운드 | 공통 효과음 | 타이밍에 맞춘 사운드 디자인 |

- **별도의 두 시스템을 만들지 않는다.** 하나의 연출 디렉터와 기본 타임라인을 두고 종족·기술 단위 **오버라이드 데이터**(AnimationProfile)만 얹는다. 피카츄가 컬렉션 모드에 나와도 자동으로 고급 연출이 적용된다.
- 포켓몬별 애니메이션을 따로 만들지 않는다. 움직임의 강도·속도·기준점 등을 **데이터로 조정**한다.
- **구현 (M3-2):** `Assets/Content/Data/animation.json` → `AnimationCatalog`(순수 C#). 종 프로필(`animProfile` 키)마다 `windupSec`(기 모으기 시간), `lungePx`(돌진 거리), `hitShakePx`(맞을 때 흔들림), `knockbackPx`(넉백), `moveFx`(기술 id → 전용 이펙트 id) — 빠진 값은 `defaults`. 18타입마다 이펙트 색(primary·secondary).
  - `AnimationDirector`가 기본 타임라인(접촉 = 돌진+타격 / 발사 = 구체 / 효과 = 고리)을 돌리고, `moveFx`가 있으면 전용 이펙트로 바꾼다. 현재 전용 이펙트: 피카츄 10만볼트 `lightning_strike`(기 모으기 → 낙뢰 → 화면 번쩍임), 거북왕 하이드로펌프 `water_cannon`(반동 → 물줄기 → 물보라).
  - 피격: `Pokepedia/Sprite Flash` 셰이더(본체 위에 겹친 렌더러, 알파가 번쩍임 세기)로 하얗게 번쩍임 + 흔들림 + 넉백, 급소는 화면 번쩍임·흔들림, 빗나감은 회피 모션. 파티클은 월드의 Unity Particle System(텍스처 없는 정사각형 입자, 월드 1 단위 = 화면 1픽셀).
- 타입별 이펙트는 **공통 프리팹 하나 + 타입별 색·모양 파라미터**로 데이터화한다.
- 모든 로스터 포켓몬은 블랙·화이트 애니메이션 스프라이트를 기본 대기·등장 모션으로 가진다 (8.2).
- Showcase 완료 정의의 세부 항목과 **마일스톤별 시간 상한은 정하지 않는다** [확정].

### 5.3 전투 흐름과 화면 구성 [확정: 에이전트 설계, 세부는 M3에서 조정]

대중적인 포켓몬 전투 흐름을 따른다. **트레이너는 등장하지 않는다**(지우 인트로 없음 [확정]. 대신 포켓몬끼리의 VS 도입 장면은 둔다, M5). 야생 포켓몬과 마주친 것처럼 진행한다.

```text
타이틀 (START → 오디오 시작)
   ↓
[Collection] 포켓몬 선택 (보유 ∩ 지원, 미보유는 잠금)   [Demo] 피카츄 vs 거북왕 고정
   ↓
VS 도입 장면 (약 2초, 확인 입력으로 건너뛰기, M5)
   ↓
"야생의 ○○이(가) 나타났다! 가라! ○○!"
   ↓
행동 선택: 싸우다 / 도망
   ├ 싸우다 → 기술 선택 → 턴 처리 → (반복)
   └ 도망   → "무사히 도망쳤다!" → 상대 포켓몬이 바뀌어 새 배틀 시작
   ↓
기절 "○○은(는) 쓰러졌다!"
   ├ 승리 → [다음 상대와 싸운다] / [처음으로]
   └ 패배 → [다시 도전] / [처음으로]
```

- **난이도는 하나** [확정]. NPC AI는 예상 데미지(위력·명중률·자속·상성 반영)가 가장 큰 기술을 고른다.
- **도망 [확정]:** Collection 모드에서는 도망치면 "무사히 도망쳤다!" 후 상대가 다른 포켓몬으로 교체되어 새 배틀이 시작되고, 플레이어 포켓몬은 HP가 가득 찬 상태로 시작한다. Demo 모드는 매치업이 고정이므로 도망을 비활성화하고 "도망칠 수 없다!" 메시지를 보여 준다.
- 현재는 1:1이므로 포켓몬 교체·가방 메뉴가 없다. 행동 메뉴는 **싸우다 / 도망** 두 가지다. **교체·가방 메뉴는 향후 확장으로 추가한다** (3:3 배틀과 함께, 5.4).
- **기술 선택:** 2×2 격자, 기술은 기본기 + 속성 기술 2개(3개, 6.3). 선택 중인 기술의 타입·위력·명중률을 보여 준다 (PP 없음).
- **턴 처리 메시지:** "○○의 ○○!" → 빗나가면 "공격은 빗나갔다!" → 급소면 "급소에 맞았다!" → 상성에 따라 "효과가 굉장했다!" / "효과가 별로인 듯하다…" / "효과가 없는 것 같다…" → HP 바 감소 애니메이션 → 기절 문구. 메시지는 타자기식으로 출력한다 (Pokepedia 퀴즈에도 타자기 훅이 있음).
- **화면:** 게임보이식 레이아웃. NPC는 오른쪽 위(앞모습), 플레이어는 왼쪽 아래(뒷모습), 이름·레벨(`:L50`)·HP 바·HP 숫자 표시, 하단에 메시지 창과 메뉴.
- **기준 해상도 240×216 [위임 → M3 결정]:** 게임보이와 같은 10:9 비율에 160×144의 1.5배. BW 스프라이트가 최대 112px(뮤츠·리자몽 앞모습)이라 160×144에는 1배로 들어가지 않는다. 화면은 이 크기를 **정수 배율**로만 키운다(`PixelCanvasScaler`). 문구는 Galmuri11 12px.
- **메시지 키:** 문장은 `BattleTextKeys`의 로케일 키로 만든다. 상대 쪽은 "야생의 ○○"처럼 별도 키를 쓴다(원작이 상대를 "야생의/やせいの/The wild"로 구분하고, 영어는 문장 앞뒤 대소문자가 달라 접두어 방식으로는 번역이 안 된다). 영어 문구는 포켓몬 블랙 대사 덤프로 확인, 일본어 일부는 기억 기반이다.
- **입력:** 방향키 + Z/X, 마우스 클릭, 터치. 모바일 브라우저(세로·가로)에서도 완벽하게 보이도록 반응형으로 만든다.
- 승리해도 보상·점수는 없다 (연속으로 다음 상대와 싸울 수 있다).

### 5.4 개발 방침과 범위

**Vertical Slice 우선** [확정]: 시각적 완성도가 가장 큰 리스크이므로 콘텐츠 확장보다 먼저 **피카츄 vs 거북왕**을 최종 품질에 가깝게 완성한다. 단계별 계획(M0~M6)과 현황은 [ROADMAP.md](ROADMAP.md)가 단일 출처다.

**용량은 최하위 고려 [확정, 2026-10-17]:** 아래 전송 크기 목표는 근거가 약한 추정이어서 결정 기준으로 쓰지 않는다. 화면 품질(출력)에 도움이 되면 M0에서 용량 때문에 뺀 설정을 다시 붙인다(후처리용 `PostProcessData`는 이미 재연결). 호스팅의 단일 파일 한도(10.2)는 실제 제약이라 확인한다. 로딩 시간·프레임·메모리 목표는 유지한다.

**성능 목표 [추정 기준 — 공식 표준 아님, 프로젝트 성패 기준 아님]**

> 업계 가이드(FRVR의 초기 다운로드 약 8 MB 권장, CrazyGames의 빈 프로젝트 사례 12.5~14.7 MB)와 일반적인 웹 로딩 감각을 바탕으로 한 추측성 기준이다. 달성하지 못해도 프로젝트 실패로 보지 않는다. 사용자 브라우저에서 실행되는 성능이므로 일반 노트북·중급 휴대폰에서도 확인하며, 서버는 정적 파일만 전달하므로 영향은 전송량과 응답 속도뿐이다.

| 항목 | 목표 | 허용 | 재검토 |
|---|---|---|---|
| 전송 크기 (압축 후, 첫 로딩) | ≤ 8 MB | ≤ 15 MB | 15 MB 초과 |
| 첫 로딩 시간 (캐시 없음, 데스크톱 Wi-Fi, 메뉴 조작 가능까지) | ≤ 5초 | ≤ 10초 | 10초 초과 |
| Fast 4G 스로틀링 로딩 | ≤ 10초 | ≤ 15초 | 15초 초과 |
| 재방문 (캐시 있음) | ≤ 3초 | ≤ 5초 | 5초 초과 |
| 프레임 | 데스크톱 60fps 안정 | 모바일 30fps 이상 | 그 미만 |
| 메모리 | 여러 판 반복해도 계속 늘지 않음 | 탭 약 300 MB 이하 (추정) | 판마다 증가(누수 의심) |

- 측정: Chrome 개발자 도구 Network 탭(캐시 비활성화, Fast 4G 스로틀링), Chrome 작업 관리자 또는 Unity Profiler.
- Unity 6 문서의 WebGL 힙 기본값은 초기 32 MB, 최대 2048 MB, 증가 단위 상한 기본 96 MB다. 이 게임의 실제 메모리는 아직 측정하지 않았다.
- 기준을 넘으면 (1) 최적화(불필요한 패키지 제거, 텍스처 압축. 스트리핑 High·Disk Size LTO는 문제 가능성 때문에 2026-10-17에 되돌렸다) → (2) 지연 로딩·범위 축소 → (3) 플랫폼 우선순위 재검토 순으로 대응한다. Cloudflare의 단일 파일 25 MiB 한도(10.2)도 함께 확인한다.

**이후 / 향후 확장.** 1순위는 1:1 배틀의 완성도이며, 그 이후에 다음을 확장한다.
- **3:3 배틀**, **포켓몬 교체 메뉴와 가방 메뉴** (3:3과 함께 추가) [확정: 향후 확장 계획, 시점·규칙은 미정]. 엔진은 처음부터 여러 포켓몬(파티)을 지원하는 구조로 설계해 둔다 (7.2).
- 로스터 추가, 기술 다양화, 포켓몬별 고유 모션, 퀴즈 보상 화면의 배틀 안내(게임 완성 후 결정).

**범위 제외.** 151마리 전체 지원, 포켓몬별 고유 애니메이션 151개, 트레이너·인트로 씬, 난이도 선택, 배틀 승리 보상·랭킹 갱신, 온라인 PvP·실시간 멀티플레이, 자체 게임 서버, 퀴즈의 Unity 재구현, LLM 기반 NPC, PP·상태이상, 3D 모델·3D 카메라, 3D 실시간 라이트·그림자, 볼류메트릭 안개.

### 5.5 화면 연출: 2.5D와 월드/HUD 분리 [의도·구조 확정, 세부는 M3에서 조정]

**결정 (2026-10-17)**
- 포켓몬은 **2D 스프라이트 그대로** 두고 배경·바닥·그림자·카메라·조명·셰이더로 입체감을 만드는 **2.5D**를 한다. 3D 모델은 쓰지 않는다.
- **렌더링을 월드와 HUD로 분리한다 [확정].** 월드(스프라이트·배경·카메라·조명·VFX)는 `SpriteRenderer`와 카메라로, HUD(HP 바·메뉴·메시지 창)는 기존 uGUI로 둔다. 이유: Light2D·Sorting Layer·월드 파티클은 SpriteRenderer가 필요하고, 후처리(Volume)를 월드에만 걸어 HUD 글자를 건드리지 않기 위해서다. 배경을 uGUI로 먼저 만들면 버려지므로 **배경·안개·그림자보다 먼저** 분리한다.
- 동기는 "Unity를 폭넓게 경험"(1장)이며 용량·작업량보다 우선한다. 용량은 최하위로 고려한다(5.4).

**구성 요소 (우선순위순)**

| 요소 | 방법 |
|---|---|
| 그림자 | 포켓몬 아래 타원 그림자(공중·지면 구분). 비용 대비 효과가 가장 크다 |
| 원근 바닥 | 타원형 발판·사다리꼴 필드. 5.3 배치(NPC 오른쪽 위·작게, 플레이어 왼쪽 아래·크게)가 이미 원근 구도다 |
| 배경 3~5 레이어 | 하늘·먼 풍경·중경·바닥. Sorting Layer로 나누고 레이어별 이동량을 달리한다(패럴랙스) |
| 카메라 연출 | 공격 직전 줌, 피격 흔들림, 승리 패닝 |
| 조명·빛 반사 | Light2D. 과장된 스타일(물 하이라이트, 전기 glow, 고스트·에스퍼 rim)이며 사실적 PBR은 아니다 |
| 안개 | 반투명 오버레이 + 후처리 Volume(비네트·색 보정). 배경별 색(숲 초록, 동굴 파랑, 고스트 보라, 물 밝은 대기). 3D 볼류메트릭은 하지 않는다 |
| 셰이더(Shader Graph) | 피격 하양 번쩍임(`Sprite Flash`는 구현됨), 타입별 glow·하이라이트 |
| 타입별 VFX | 공통 프리팹 + 타입별 색·모양 파라미터(5.2). 로스터 타입(전기·물·불꽃·비행·풀·독·고스트·에스퍼)만 |

**구현 순서 [권장안]** (M3 안, 시간 상한 없음)
1. **월드/HUD 분리 — 완료(M3-4)**: 화면은 똑같이 보이게 이관했다. 스프라이트·발판·VFX·피격 번쩍임·`AnimationDirector`의 이동을 월드로, HP 바·메뉴·메시지는 HUD(Overlay 캔버스)에 남겼다. 월드는 `BattleWorld`(`SpriteRenderer`)와 `PixelCamera`, HUD 정렬은 `PixelAlign`이 맡는다.
2. 그림자, 원근 바닥, 배경 레이어, 카메라 연출 — **완료(M3-5)**.
3. 안개, Light2D, 후처리, 타입별 glow — **완료(M3-5)**.
4. 피카츄 vs 거북왕 대표 장면(예: 비 오는 배경, 약한 안개, 전기 글로우, 물대포 반사, 줌, 승리 연출). Standard는 공통 배경 1~2종 + 타입 파라미터. 비 오는 저녁 배경·안개·전기 글로우·물대포 glow·승리 연출은 구현했다(M3-5).

**유의 (조사·검증 결과)**
- **도트를 깨뜨리지 않는다.** Point 필터 + 정수 배율을 유지한다. 원근은 스프라이트 크기를 연속으로 바꾸지 않고 배치와 고정 크기 차이로 표현하며, 패럴랙스·줌은 정수 픽셀 단위로 움직인다. URP 2D에는 `Pixel Perfect Camera` 컴포넌트가 있고 Reference Resolution(우리는 240×216)과 Upscale Render Texture 옵션을 제공한다(공식 문서). 6.0 문서에는 픽셀 배치가 어긋날 수 있다는 경고가 있었고 6.3 문서에는 없다. 이 프로젝트에서 쓸지는 이관할 때 검증한다 [미확인].
- **후처리와 HUD:** HUD는 Screen Space Overlay 캔버스라 월드 카메라의 후처리를 받지 않는다. 화면에서 확인했다(Bloom이 걸린 장면에서도 HUD 글자는 선명). 월드와 HUD의 정수 배율·홀수 크기 창 정렬도 800×600과 733×611에서 어긋나지 않았다. 카메라 스택은 쓰지 않았다.
- **엔진·`BattleEvent`는 바꾸지 않는다.** 타입은 이벤트에 넣지 않고 `MoveUsed`의 기술 id로 기술 데이터(`type`, `animKind`)와 `animation.json`을 조회해 연출을 조합한다(7.3).
- **성능:** 후처리를 쓰므로 `PostProcessData`를 다시 연결했다(5.4). 투명 오버레이·Light2D·후처리는 모바일 fill-rate 부담이 있어 모바일 30fps 기준(5.4)으로 측정해야 한다 **[미측정: 브라우저 패널이 숨겨진 상태라 프레임을 잴 수 없었다]**. 화면을 읽는 왜곡(고스트 등) 셰이더는 별도 렌더 텍스처가 필요할 수 있어 [미확인] 필요성이 확인될 때만 한다.
- **이관 결과 (M3-4):** `UiSpriteAnimator` → `SpriteAnimator`, `UIFlash` 셰이더 → `Sprite Flash`(URP 2D 언릿, 본체 위 겹침), `VfxLayer`의 번개·구체·고리는 `SpriteRenderer`, 월드 이펙트는 HUD(정보 상자·메시지) 뒤에 그려지고 화면 전체 번쩍임만 HUD 맨 위에 남는다. 월드 카메라는 창 크기에 맞춰 정수 배율로(`PixelCamera`), 창 크기가 홀수일 때의 반 픽셀은 월드와 HUD가 같이 옮겨 맞춘다. `Pixel Perfect Camera` 컴포넌트는 쓰지 않았다(직접 계산이 HUD 배율과 같은 식을 쓰기 쉬워서).

**구현 결과 (M3-5, 테마 "비 오는 저녁" 하나)**
- **배경 레이어** (`BattleBackdrop`, 파일 없이 코드로 그린 도트 텍스처): 하늘 → 구름(천천히 흐름) → 먼 언덕 → 나무 숲 → 원근 바닥(소실점으로 모이는 풀 줄무늬, 지평선 안개). 레이어마다 카메라를 따라가는 비율이 달라(0.05 / 0.15 / 0.3 / 0.55 / 1) 공격 때 카메라가 ±5px 움직이면 깊이가 보인다.
- **날씨·분위기**: 안개 2겹(뒤 0.22, 앞 0.10, 서로 다른 속도로 흐름), 비 파티클, 바닥의 빗방울 물결(원근으로 납작), 가끔(7~14초) 번개 번쩍임, 가장자리 비네트(스프라이트라 창 크기와 무관).
- **그림자**: 포켓몬 아래 타원(스프라이트 폭에 비례). 승리 때 뛰는 동안 그림자는 바닥에 남는다.
- **조명** (`BattleLighting`): 전역 조명(차가운 푸른빛, 곱하기) + 타입 색 점 조명 `Pulse`(기 모으기, 낙뢰, 물대포, 접촉·발사·효과, 급소, 승리). 점 조명은 더하기 블렌드라 밝기가 1을 넘는 부분만 Bloom이 번진다. 배경·발판·포켓몬은 Sprite-Lit, 이펙트·그림자·안개·비·비네트는 Sprite-Unlit.
- **후처리** (`BattlePostFx`): 월드 카메라 전역 Volume — Bloom(threshold 1.0)과 약한 채도·대비. 비네트는 Volume이 아니라 스프라이트다(Volume 비네트는 창 전체 가장자리에 걸려 게임 화면 가장자리에 맞지 않는다).
- **카메라 (M5 공격 카메라, 2026-10-17)**: 카메라(`PixelCamera`)는 정수 배율로 고정하고 월드의 Pan 노드를 옮기고 키워서 카메라가 움직이는 것처럼 보이게 한다(`BattleWorld.CameraTo`·`Punch`). HUD는 다른 캔버스라 움직이지 않는다. 기술마다 준비 동작 동안 공격자 쪽으로 다가가며 1.12배, 발사 순간(공격음과 같은 `ReleaseSec`) 상대 쪽으로 0.16초에 넘어가 1.08배, 맞는 순간 +4%(급소 +8%) 당김, 끝나면 0.3초에 가운데·1배로 돌아온다. 승리 때는 이긴 쪽으로 1.1배. 1배가 아니면 도트 크기가 고르지 않아 확대는 움직이는 짧은 순간에만 쓰고, 멈춰 있을 때는 항상 1배다. 기울기(회전)는 도트 계단이 깨져 쓰지 않는다. 확대해도 배경 밖이 보이지 않게 중심 이동 범위를 제한한다(좌우는 배경 레이어 여유 24px까지). 배경 레이어는 중심의 가로 이동만큼 패럴랙스로 따라간다.
- 이 테마는 Showcase 대표 장면용이다. Standard는 공통 배경 1~2종(M5)에서 `BackdropTheme`만 추가한다.
- **직접 확인한 것:** WebGL Dev 빌드에서 배경 전체, 비·물결·안개·비네트, 그림자, 기 모으기 glow, 공격 때 카메라 이동과 패럴랙스, 낙뢰 볼트, 피격 번쩍임, 기절(그림자도 같이 사라짐), 패배 후 [다시 도전], 홀수 크기 창. **직접 못 본 것:** 번개 번쩍임 타이밍. 승리·급소 연출은 연출 실험실에서 확인했다(2026-10-17).
- **프레임 측정 (2026-10-17, Release 빌드, 데스크톱 크롬 계열 내장 브라우저, 창 1141×1027 → 4배율, 75Hz 모니터):** 전투 대기(비·안개·조명·후처리)와 실험실 연출 8종(10만볼트 3종, 하이드로펌프 4종, 승리) 모두 평균 75 FPS(모니터 상한). JS `requestAnimationFrame` 기준 20ms를 넘는 프레임 0개, 게임 안 `[fps]` 5초 측정에서 가장 느린 프레임은 보통 15~16ms, 가끔 21~24ms(한 프레임 밀림), 배틀 시작 직후 한 번 34ms. **모바일(사용자 측정, 같은 날):** 아이폰 Safari(Dynamic Island 모델, 기기명 미확인)에서 같은 와이파이로 Release 빌드를 열어 `?fps`로 봤다. 평균 50~60 FPS, 화면에 보인 값은 57~59 FPS·가장 느린 프레임 18~21ms. Safari는 기본적으로 60Hz로 그리므로 상한 근처이고, 연출이 겹칠 때 몇 프레임씩 밀리는 정도다. → **후처리·조명은 줄이지 않는다**(에이전트 판단). 저사양 안드로이드는 재지 않았다(M4 실배포 후 필요하면 다시 본다).

## 6. 전투 규칙과 데이터 설계

### 6.1 원칙 [확정]

- 원작 규칙 재현이 목표가 아니다. 엔진은 **하나**만 작성하고 포켓몬은 **데이터**로만 표현한다. 포켓몬별 클래스·스크립트를 만들지 않는다.
- **데이터 기준: 현대 기준.** 등장 포켓몬은 1세대 151종 중 선별한 일부, **타입·능력치·상성은 현대 기준**(18타입, 능력치 6종), 전투 규칙은 직접 정의한 단순화 규칙이다. 게임보이 감성은 스프라이트·UI·폰트·색감·애니메이션·사운드로 유지한다. (로스터 6마리는 원작 1세대와 현대 기준에서 타입 구성이 같다: 전기, 물, 불꽃/비행, 풀/독, 고스트/독, 에스퍼. 원작 1세대는 15타입이며 능력치의 특수가 하나였다 — 기억 기반.)
- 기술 이름·구성은 원작과 일치할 필요가 없다. 이름은 장식이고 규칙은 데이터(타입·위력·명중률·분류)가 결정한다.

### 6.2 포켓몬 데이터

- 위치: `Assets/Content/Data/species.json`, `moves.json`, `roster.json`. 로더는 `Pokepedia.Content.ContentLoader`(순수 C#, 엄격한 스키마: 누락·모르는 필드·잘못된 값은 항목 이름을 담은 `FormatException`).
- 출처: 종족값·타입은 **PokeAPI**(`/pokemon/{id}`, Pokepedia DB와 같은 출처)로 확인해 손으로 적었다(2026-10-16, 로스터 6종 불일치 0). Pokepedia DB 스냅샷 export 스크립트는 필요해지면 만든다 [권장안]. 런타임 DB 조회는 없다.
- 이름 문자열은 엔진에 없다. `nameKey`(`species.025`, `move.thunderbolt`)로 로케일 파일(`Assets/Content/Locale/{ko,en,ja}.json`)에서 찾는다. 이름은 PokeAPI의 ko / en / ja-Hrkt(가나 표기) 값이다.
- **지원 포켓몬 목록은 `roster.json`** (id, 등급 `showcase`|`standard`, NPC 출현 가중치 `npcWeight`)으로 관리한다. 엔진은 이 파일을 모른다.
- species 에는 기술 목록이 없다. 기술은 타입에서 자동 배정한다(6.3).

```json
// species.json (실제 항목)
{ "id": 25, "types": ["electric"],
  "baseStats": { "hp": 35, "attack": 55, "defense": 40, "spAttack": 50, "spDefense": 50, "speed": 90 },
  "sprites": { "front": "front_25_sheet", "back": "back_25_sheet", "frontShiny": "front_25_shiny_sheet", "backShiny": "back_25_shiny_sheet" },
  "animProfile": "pikachu", "nameKey": "species.025", "legendary": false }

// roster.json — npcWeight 는 임시값(뮤츠 2, 나머지 10). 로스터 확장(M5)에서 시뮬레이션으로 조정한다.
[ { "id": 25, "tier": "showcase", "npcWeight": 10 }, { "id": 9, "tier": "showcase", "npcWeight": 10 }, ...
  { "id": 150, "tier": "standard", "npcWeight": 2 } ]
```

### 6.3 기술 데이터 (새로 작성)

- Pokepedia에는 기술 데이터가 없으므로 **직접 정의**한다. **노말 기본기 1개 + 로스터가 쓰는 타입별 대표 기술 1개씩 + 단일 타입 종이 쓰는 타입의 보조 기술 1개씩**이며 기본 로스터면 **12개**다. 새 타입을 추가할 때 해당 기술·이펙트를 추가한다.
- 각 포켓몬은 **기본기 + 속성 기술 2개 = 3개**를 받는다 [확정: 사용자 결정 2026-10-17]. 이 매핑은 타입에서 **자동 생성**한다.
- 기술 필드: `id, type, category(physical|special), power, accuracy, nameKey, animKind, role(basic|signature|secondary)`. **명중률과 급소를 포함한다** [확정].
  - `role`: 기본기는 정확히 1개(`basic`), 대표 기술(`signature`)·보조 기술(`secondary`)은 타입마다 각각 최대 1개. 배정 순서는 기본기 → 종의 타입 순서대로 대표 기술 → (단일 타입이면) 그 타입의 보조 기술. 예: 리자몽 = 몸통박치기, 화염방사, 날개치기 / 피카츄 = 몸통박치기, 10만볼트, 번개.
  - 보조 기술은 대표 기술보다 **기대 데미지(위력 × 명중)가 낮게** 잡는다. NPC AI는 기대 데미지가 가장 큰 기술을 고르므로 보조 기술이 생겨도 Demo 밸런스(6.5)는 그대로다. 플레이어에게는 "한 방이 크지만 빗나가는 기술(번개)"이나 "약하지만 반드시 맞는 기술(물대포·염동력)" 같은 선택지가 된다.
- **수치 [위임 → M2 결정]:** 기본기 위력 16·명중 100, 타입별 대표 기술 위력 **35**·명중 95. 원작 위력(40/90 정도)보다 낮게 잡아 전투를 4~6턴으로 맞춘다. 예외: **10만볼트 명중 100, 하이드로펌프 명중 85**(원작처럼 믿음직한 기술과 세지만 빗나가는 기술로 나눔, M3 피드백). 근거는 6.5.

### 6.4 전투 규칙 [확정]

공식은 현대 포켓몬 게임(능력치 3세대 이후, 데미지 6세대 이후) 기준이며 M2에서 검증했다. 출처: Pokémon Showdown 시뮬레이터 소스(`sim/battle.ts` statModify·modify, `sim/battle-actions.ts` getDamage·modifyDamage), 상성은 PokeAPI `type` damage_relations와 Pokémon Database 표(324칸 일치). Bulbapedia는 자동 조회가 막혀(403) 직접 대조하지 못했다. 코드 주석에 URL이 있다.

- **능력치 환산:** 레벨 50 고정, 개체값 31, 노력치 0, 성격 보정 없음. 종족값은 먼저 압축(6.5)한다.
  - HP = ⌊(2×종족값+31)×레벨/100⌋ + 레벨 + 10
  - 그 외 = ⌊(2×종족값+31)×레벨/100⌋ + 5
  - 예(압축 없음): 피카츄 L50 = HP 110 / 공격 75 / 방어 60 / 특공 70 / 특방 70 / 스피드 110, 거북왕 L50 = HP 154 / 103 / 120 / 105 / 125 / 98.
  - 예(K=0.65 압축, 실제 게임 값, `StatCalculatorTests.Compute_CurrentDefault_DemoPair`): 피카츄 = 126 / 84 / 74 / 81 / 81 / 107, 거북왕 = 154 / 102 / 113 / 103 / 116 / 99.
- **물리/특수:** 기술별 `category`를 데이터에 지정한다. physical은 공격÷방어, special은 특공÷특방.
- **턴 순서:** 스피드가 높은 쪽이 먼저 행동하고 동률이면 무작위.
- **행동 처리:** 명중 판정(기술 명중률%, 회피·명중 단계 없음) → 빗나가면 `MoveMissed` → 명중하면 급소 판정 → 데미지 계산.
- **급소:** 확률 1/16, 데미지 ×1.5 [권장안: 현대 6세대 방식, 값 조정 가능].
- **데미지 공식:** ((2L/5+2) × 위력 × 공격/방어 ÷ 50 + 2) × 급소(×1.5) × 난수(0.85~1.0) × 자속 보정(×1.5) × 타입 상성. L은 레벨, 상성은 ×2 / ×0.5 / ×0이며 이중 타입은 곱한다. 게임처럼 **단계마다 정수 처리**한다(`DamageCalculator`):
  1. 기본 = ⌊⌊⌊⌊2L/5+2⌋ × 위력 × A⌋ / D⌋ / 50⌋ + 2
  2. 급소 ⌊×1.5⌋ → 3. 난수 ⌊×R/100⌋ (R = 85~100) → 4. 자속 ×1.5 (4096 고정소수점, 0.5는 내림) → 5. 상성 ⌊×배수⌋
  6. 상성 0이면 0, 그 외 최소 1. 순서가 결과에 영향을 준다(난수가 자속보다 먼저).
- 명중·급소·데미지 난수는 모두 `IRandom`으로 주입해 테스트에서 고정한다. HP 0이면 패배.
- **난수 소비 순서**(엔진, 테스트로 고정): 스피드 동률일 때만 `Next(2)`(0이면 플레이어 선공) → 행동마다 명중률 < 100이면 `Next(100)` → 명중하면 급소 `Next(16)` → 데미지 난수 `Next(16)`(85 + 값).
- 상성이 0(효과가 없음)이면 급소가 떠도 급소로 표시하지 않는다. 피해량 이벤트는 실제로 깎인 HP(남은 HP 이하)다.
- **타입 상성:** 18×18 표를 직접 작성하고 단위 테스트로 검증한다.
- **제외:** PP, 상태이상, 우선도, 능력치 단계 변화, 날씨.
- **NPC AI:** 하나의 수준. 예상 데미지(위력·명중률·자속·상성 반영)가 큰 기술을 고른다.

### 6.5 밸런스와 NPC 선택 [확정 방침 / 세부는 에이전트가 조정]

- **전투 길이:** 쇼케이스는 약 **4~6라운드**. 별도의 HP 배율 규칙은 **두지 않고 기술 위력 값(데이터)** 으로 맞춘다 (위력 ×0.4가 HP ×2.5와 같은 결과를 냈다). 모든 모드가 같은 규칙과 기술 데이터를 쓰므로 Demo만의 값은 없다.
- **균형:** 종족값을 중간값 쪽으로 당기는 **압축** `stat' = 80 + (종족값 − 80) × k`을 쓴다. 반올림은 사사오입, 최소 1. **k = 0.65** (M2 결정, 아래 "M2 밸런스 결과").
- **NPC 선택 (Collection):** 로스터에서 가중 추첨한다. **뮤츠 같은 전설 포켓몬은 드물게만 등장**하도록 가중치를 낮춘다 [확정]. 압축 계수, 위력·명중 값, 상성 편향, 이상치 보정 등 **밸런스 세부는 에이전트가 시뮬레이션으로 조정하고 완료 후 이 문서에 정리한다** [위임].
- 중복 스티커(quantity)는 능력치에 영향 없음, shiny는 외형만 변경.
- **Demo Mode:** 피카츄(플레이어) vs 거북왕(NPC) 고정. **피카츄 승률 85~93%** 를 시드 고정 시뮬레이션 테스트로 검증·조정한다 [확정, 2026-10-17 사용자 피드백으로 60~70%에서 상향].
- 신규 사용자(스티커 없음)와 단독 실행은 Demo Mode로 처리한다. Collection에서 보유 ∩ 지원이 0마리면 자동 전환하지 않고 안내와 [데모 체험] 선택지를 보여 준다 (9.2).

종족값 합은 피카츄 320 ~ 뮤츠 680(Pokepedia 현재 기준)으로 격차가 커서 압축 계수 k를 쓴다.

**M2 밸런스 결과 (2026-10-16, `BalanceTests`, 5,000판 시드 고정)**

| 항목 | 값 |
|---|---|
| 정한 수치 | k = 0.65, 대표 기술 위력 35·명중 95, 기본기 위력 16·명중 100, 급소 1/16 ×1.5, 난수 85~100% |
| 피카츄 vs 거북왕 | 피카츄 승률 **68.5%**, 평균 **4.92턴** (최소 3, 최대 7) |
| 시뮬레이션 가정 | 양쪽 모두 NPC AI(기대 데미지 최대 기술)로 행동. 플레이어도 "가장 센 기술을 고르는 사람"으로 본다 |

- **수치가 민감하다.** 몇 번 맞으면 쓰러지는지(확정 n타)가 한 단계 바뀌면 승률이 크게 뛴다(예: k 0.6에서 위력 38 → 62%, 40 → 47%). 그래서 목표 범위 안의 한 점이 아니라 **주변까지 60~70%가 유지되는 구간의 중심**을 골랐다: k 0.64~0.68 × 위력 34~36이 모두 60~70%.
- 다른 기술·포켓몬을 추가하거나 수치를 바꾸면 `BalanceTests`가 범위 이탈을 잡는다. 조정용 표 출력(`Sweep_CompressionAndSignaturePower`, k × 위력 표)은 최소 테스트 원칙에 따라 지웠다. 다시 조정할 때는 커밋 `cd45839`의 `Assets/Tests/EditMode/BalanceTests.cs`에서 꺼내 임시로 쓴다.
- 나머지 4마리와의 매치업, 전설 가중치(`npcWeight`, 임시 뮤츠 2 / 나머지 10)는 로스터 확장(M5)에서 조정한다.

**M3 피드백 조정 (2026-10-17, 5,000판 시드 고정)**

- **문제(사용자 플레이):** 60~70%에서는 피카츄가 10만볼트만 계속 써야 HP 2쯤 남기고 겨우 이기고, 한 번이라도 빗나가면 진다. 시뮬레이션도 같았다: 승률 68%, 이긴 판의 남은 HP 평균 15%, **피카츄가 한 번이라도 빗나간 판의 승률 17%**.
- **조정:** k·위력은 그대로 두고 명중만 바꿨다. 10만볼트 95 → **100**, 하이드로펌프 95 → **85**. 결과: 피카츄 승률 **88.5%**, 평균 4.93턴, 이긴 판의 남은 HP 약 25%. 다른 매치업에는 영향이 거의 없다(두 기술은 피카츄·거북왕만 쓴다).
- 비교한 다른 안: 10만볼트 명중 100만(82.5%, 남은 HP 15% — 여전히 아슬아슬), k 0.6(85.6%, 모든 매치업이 바뀜), 하이드로펌프 위력을 올리고 명중을 내리기(승률 52~70%, 판마다 편차가 큼).

## 7. 아키텍처

### 7.1 설계 원칙 [확정]

1. **엔진(규칙)과 콘텐츠(데이터·에셋·텍스트)를 처음부터 분리**한다. 엔진은 ID와 숫자만 안다.
2. **Domain은 UnityEngine을 참조하지 않는다.** Assembly Definition으로 강제한다.
3. 난수는 `IRandom`으로 주입해 테스트에서 고정한다.
4. 규칙 자체를 일반화하지 않는다 (`IRuleSet` 등 금지). 분리 대상은 규칙이 아니라 콘텐츠다.
5. 모든 클래스에 인터페이스를 만들지 않는다. DI 프레임워크, Repository 패턴, 이벤트 버스 라이브러리, ECS는 도입하지 않는다.
6. **엔진은 지원 포켓몬의 수를 모른다.** 로스터가 늘어도 엔진은 수정하지 않는다.
7. 우선순위: **배틀 로직의 독립성, 테스트 용이성, 화면과 도메인의 책임 분리.** Java/Spring의 DDD는 참고만 한다.

### 7.2 계층

```text
Presentation (Unity)   ← 월드 뷰(스프라이트·배경·카메라·조명·VFX) + HUD 뷰(uGUI), 이벤트 재생, 연출(AnimationDirector), 오디오
        ↓
Application (C#)       ← BattleController, NpcBattleAi, 배틀 흐름
        ↓
Domain (Pure C#)       ← BattleEngine, DamageCalculator, TypeChart, BattleState
        ↑ 읽기 전용 데이터 주입
Content (Data)         ← species.json, roster.json, moves.json, typechart, locale, 스프라이트, AnimationProfile

Bridge (Platform)      ← IHostBridge: WebGL(jslib ↔ postMessage) / Editor(Null 구현)
```

- **Domain:** 입력 `BattleState` + `BattleAction`, 출력 `BattleEvent` 목록. 엔진은 문자열·스프라이트를 모른다. 여러 포켓몬(파티)을 지원하는 구조로 설계한다.
- **Application:** 플레이어 행동 접수, NPC 행동 결정, 엔진 호출, 이벤트 전달, 배틀 종료·재시작·상대 교체 처리.
- **Presentation:** `BattleEvent`를 받아 애니메이션·파티클·셰이더·사운드·HP 바로 **재생만** 한다. 규칙 판단 금지. 5.5에 따라 **월드 뷰**(`SpriteRenderer`·카메라·조명)와 **HUD 뷰**(uGUI: HP 바·메뉴·메시지)로 나눈다.
- **Bridge:** React와의 통신을 한 곳에 격리한다. 에디터에서는 Null 구현.

### 7.3 엔진 ↔ 화면: 이벤트 로그와 연출 디렉터

실제 정의는 `Assets/Scripts/Domain/Battle/BattleEvents.cs`. Side 0 = 플레이어, 1 = NPC.

```csharp
public abstract record BattleEvent;
public sealed record PokemonSentOut(int Side, int SpeciesId, int Hp, int MaxHp) : BattleEvent; // NPC 먼저, 다음 플레이어
public sealed record TurnStarted(int Turn) : BattleEvent;
public sealed record MoveUsed(int Side, string MoveId) : BattleEvent;
public sealed record MoveMissed(int Side, string MoveId) : BattleEvent;
public sealed record DamageDealt(int TargetSide, int Amount, int HpAfter, double Effectiveness, bool Critical) : BattleEvent;
public sealed record Fainted(int Side) : BattleEvent;
public sealed record BattleEnded(int WinnerSide) : BattleEvent;
```

엔진 API: `new BattleEngine(state, rules, random)` → `Start()`(등장 이벤트) → `PlayTurn(playerAction, npcAction)`(한 턴 이벤트, 한쪽이 전멸하면 그 자리에서 끝). 행동은 지금 `UseMove(moveIndex)`뿐이고 도망은 Application 흐름에서 처리한다. `BattleSide`는 파티(여러 마리)+출전 인덱스 구조지만 쓰러진 뒤 교체는 3:3 확장 때 넣는다.

```text
BattleEngine (Pure C#)
      │ BattleEvent 목록
      ▼
BattleController
      │ 이벤트 실행
      ▼
AnimationDirector (Presentation)
      │ 기본 타임라인(접촉/발사/효과) + (종족/기술) AnimationProfile 오버라이드
      ├── Animator   ├── Particle System   ├── Shader   ├── Audio   └── Camera Effects
```

엔진은 데미지와 남은 HP만 반환하고 연출은 Presentation이 이벤트와 AnimationProfile로 결정한다. 규칙과 시각적 연출이 완전히 분리되므로 연출을 바꿔도 엔진은 변경하지 않는다. 테스트는 이벤트 리스트만 단언하고, 메시지는 이벤트 → 로케일 키 → 문자열 순으로 Presentation에서 조립한다.

### 7.4 Java 개발자를 위한 C# 대응표

### 7.6 지원 포켓몬 매니페스트 [권장안]

지원 포켓몬 ID 목록의 **단일 출처는 Unity 저장소의 `roster.json`** 이다. React와 Unity가 각자 목록을 관리하지 않는다. 빌드와 함께 `roster.json`(또는 ID 매니페스트)을 정적 파일로 배포하고 Pokepedia가 필요할 때 읽는다 (CORS 헤더 필요). 전달 방식은 [위임].

### 7.7 폰트 (한글·일본어·영어) [확정: Galmuri11 + TMP Static]

- TMP 폰트 에셋에 글리프가 없으면 □로 깨진다. 사용자 텍스트 입력이 없고 출력 문자열이 정해져 있으므로 **필요한 글리프만**(M0 기준 419자) 담은 **TMP Static 아틀라스**를 쓴다. Dynamic은 원본 폰트가 빌드에 들어가 용량이 늘어 쓰지 않는다.
- 폰트는 **Galmuri11**(한글·가나·JIS 한자 지원, OFL-1.1). 11 Bold는 가나·한자·♀♂가 없고 11 Condensed는 한자가 없다. 배포 시 저작권 고지와 라이선스를 동봉한다 (`Assets/Content/Fonts/Galmuri-OFL.txt`).
- 글리프 추출: `ko/ja/en.json` + 포켓몬·기술 이름 + 기호 → 중복 제거 → Static 아틀라스 (`Assets/Editor/FontAtlasBuilder.cs`).
- 모든 로케일 문자열의 글리프 포함 여부는 EditMode 테스트로 확인한다. CanvasScaler가 정수 배율이 아니면 도트가 고르지 않으므로 `PixelCanvasScaler`를 쓴다.

### 7.8 테스트 전략

- Domain 테스트는 코드로 만든 가짜 종족·기술(`TestMon`, `TestMove`)만 쓴다. 실제 JSON에 의존하지 않는다.
- `ContentLoader`는 "실제 JSON이 스키마에 맞는지", 로스터의 모든 포켓몬이 필요한 스프라이트·기술·로케일 키를 가졌는지 자동 검증한다.
- `IRandom` 스텁으로 결정적 테스트를 만든다 (명중·급소·데미지 난수 모두 주입).
- 순서: 타입 상성(18×18 표본 + 이중 타입) → 데미지 → 명중·급소 → 턴 순서 → 승패 판정 → NPC AI. Demo 매치업은 시드 고정 시뮬레이션으로 승률·라운드 수를 검증한다.
- 연출은 자동화가 어려우므로 체형별 대표 포켓몬을 골라 눈으로 확인한다 (스프라이트 위치·잘림).
- Unity 화면·연출은 CI나 PlayMode로 자동화하지 않는다(Actions 한도, 테스트 최소 원칙). 에디터·브라우저에서 눈으로 확인하고, 웹 배포(M4) 전에 로컬 빌드로 한 판을 확인한다.

## 9. Pokepedia(React) 연동 — 가벼운 연동

### 9.1 방식: iframe + postMessage [권장안]

- 기존 사이트의 헤더·푸터·i18n을 유지하면서 Unity 게임을 한 페이지에 넣는다. 임베드 페이지 경로는 **`/[locale]/battle`** [확정].
- Origin 검증 필수. Pokepedia CSP(`frame-src`)와 Unity 호스트의 `frame-ancestors`를 확인한다.
- 별도 도메인에 호스팅해도 `postMessage`로 충분하다 (쿠키를 쓰지 않음).

### 9.2 메시지 규약 (v1) [확정]

이 절이 Pokepedia ↔ Unity 규약의 **단일 출처**다. Pokepedia(React) 쪽 구현은 이 절을 따른다.

#### 구성

```text
Pokepedia 페이지 (/[locale]/battle)
  └─ <iframe src="https://battle.pokepedia.dev/?host=pokepedia" allow="autoplay">
        Unity Web 빌드 (index.html 템플릿 + HostBridge.jslib + HostBridge.cs)
```

- 방향은 **단방향**이다. React가 보유 목록을 한 번 넘기고, Unity는 결과를 저장하지 않는다.
- 쿠키·인증을 쓰지 않으므로 다른 도메인에 호스팅해도 `postMessage`로 충분하다.
- 컬렉션 조회는 인증된 React(서버/RLS)가 수행한다. Unity는 인증·DB를 다루지 않는다.
- **지원 포켓몬 필터는 Unity가 처리한다.** React는 보유 목록 전체를 보내고 Unity가 로스터와의 교집합(보유 ∩ 지원)을 계산한다. 로스터가 늘어도 규약이 바뀌지 않는다.
- Unity로 전달된 보유 목록은 조작될 수 있으나 보상·랭킹에 영향이 없으므로 검증하지 않는다.

#### 모드 판별 [확정]

| iframe 주소 | 동작 |
|---|---|
| `?host=pokepedia` 없음 | 즉시 **Demo** 모드(피카츄 vs 거북왕). 대기하지 않는다 |
| `?host=pokepedia` 있음 | START 후 `ready`를 보내고 `init`을 **5초** 기다린다 |

- 5초 안에 `init`이 오지 않으면 "연결하지 못했습니다" + **[다시 시도] / [데모 체험]**을 보여 준다. **자동으로 Demo로 바꾸지 않으며** Demo는 [데모 체험] 버튼으로 사용자가 명시적으로 선택할 때만 시작한다.
- [다시 시도]를 누르면 `ready`를 다시 보낸다.
- iframe 여부(`window.parent !== window`)로는 판별하지 않는다. 포트폴리오 허브도 iframe으로 임베드할 수 있기 때문이다.
- 쿼리는 jslib로 `location.search`를 읽어 판별한다(iframe에서 `Application.absoluteURL`의 의미가 불명확해 쓰지 않는다. M0 확인).

| 모드 | 포켓몬 선택 | 사용처 |
|---|---|---|
| **Demo Mode** | 로그인 없이 **피카츄 vs 거북왕 고정 매치업** (Showcase 품질, 선택 화면 없음) | 포트폴리오 허브 등 단독 실행 |
| **Collection Mode** | Pokepedia가 `init`으로 전달한 **보유 포켓몬 ∩ 지원 포켓몬** | Pokepedia iframe |

- 별도 엔진을 두 개 만드는 것이 아니라 포켓몬 선택(로스터) 데이터만 다르다.
- Collection 선택 화면: 지원 포켓몬 목록을 보여 주고 **보유한 포켓몬만 선택 가능, 미보유는 잠금**("퀴즈로 획득"). 보유했지만 지원하지 않는 포켓몬은 "배틀 지원 N종 준비 중" 같은 한 줄로 안내한다. 보유 ∩ 지원이 비어 있으면 안내와 [데모 체험] 버튼을 보여 준다.

#### 메시지

모든 메시지는 `postMessage`로 보내는 **객체**이며 `type`과 프로토콜 버전 `v`를 가진다. 요청 ID는 현재 필요하지 않다 [위임].

**로딩 순서:** Unity Web Build 로딩 → Unity → React `ready` → React → Unity `init` → Unity가 보유 ∩ 지원을 계산하고 게임 시작.

**Unity → React: `ready`**

```json
{ "type": "ready", "v": 1 }
```

- Unity 로딩과 START가 끝났다는 뜻이다. **React는 이 메시지를 받은 뒤에만 `init`을 보낸다.** React가 `init`을 먼저 보내면 Unity 로딩 전에 사라질 수 있다.
- Unity가 재로딩되면 `ready`가 다시 온다. 그때 React는 `init`을 다시 보낸다.

**React → Unity: `init`**

```json
{ "type": "init", "v": 1, "locale": "ko", "owned": [ { "id": 25, "shiny": false }, { "id": 9, "shiny": true } ] }
```

| 필드 | 설명 |
|---|---|
| `locale` | `ko` / `en` / `ja`. 그 밖의 값은 `ko`로 처리 |
| `owned` | 사용자가 가진 **스티커 전체**. 배틀 지원 여부는 Unity가 로스터와 교집합으로 판단한다 |

- `v`가 1이 아니면 Unity는 무시한다.

**Unity → React: `battleEnded` (예정, M6)**

```json
{ "type": "battleEnded", "v": 1, "result": "win" }
```

표시용이다. 저장하지 않는다.

**Unity → React: `resize` (필요 시)** — 높이 조정. 아직 정의하지 않았다.

#### 보안

| 위치 | 규칙 |
|---|---|
| Unity 템플릿 `message` 리스너 | `event.origin`이 허용 목록(`window.pokeHost.allowedOrigins`)에 있을 때만 `init`을 Unity로 전달 |
| Unity → React 전송(jslib) | `targetOrigin`을 `'*'`로 쓰지 않고 허용 목록의 각 origin으로 보낸다(일치하는 곳에만 도착) |
| React 쪽 | `event.origin`이 Unity 호스트(`NEXT_PUBLIC_BATTLE_URL`의 origin)일 때만 `ready`를 처리 |
| Unity 호스트 응답 헤더 | `Content-Security-Policy: frame-ancestors`에 Pokepedia·포트폴리오 허브만 허용 |

허용 목록은 `Assets/WebGLTemplates/Pokepedia/index.html`에 있다. 현재 값: `https://pokepedia.dev`, `https://www.pokepedia.dev`, `http://localhost:3000`(Pokepedia 개발 서버), `http://localhost:8000`(로컬 테스트 페이지). Vercel Preview 도메인은 M6에서 정한다. 또 Pokepedia CSP의 `frame-src`도 확인한다(9.1).

#### 입력

- iframe 안에서는 방향키·Space의 기본 동작(부모 스크롤)을 막는다.
- 클릭·터치 시 캔버스에 포커스를 준다.
- React 쪽 iframe에는 `allow="autoplay"`를 준다. 첫 소리는 Unity 안의 START 버튼에서 낸다.

#### 로컬 테스트

```bash
python -I Tools/web/serve.py --dir Builds/Web --port 8001 --ancestors http://localhost:8000
python -I Tools/web/serve.py --dir Tools/web/host-test --port 8000
```

`http://localhost:8000/`를 열면 모의 Pokepedia 페이지가 게임을 iframe으로 띄운다. 이 페이지에서 `ready` → `init` 왕복, 타임아웃(init 보내지 않기 체크), 스크롤 간섭을 확인할 수 있다.

### 9.3 DB 정책 [확정]

- **Pokepedia DB는 변경하지 않는다.** 새 테이블·RPC가 필요 없고 `user_sticker`에도 아무것도 추가하지 않는다. 읽기만 사용한다 (컬렉션은 React가 읽어 전달, 카탈로그는 스냅샷 JSON).
- (Prod와 Preview가 같은 DB를 공유하고 migration이 자동 적용되므로 변경이 필요해지면 additive만 허용한다.)

### 9.4 Pokepedia 쪽 변경 범위

- 내비게이션 "배틀" 항목, 임베드 페이지(`/[locale]/battle`), 메시지 핸들러.
- 문구는 `messages/ko·en·ja.json` 세 곳에 모두 추가 (언어별 키 일치 테스트가 있음).
- 새 라우트는 구조 변경이므로 `docs/system_design.md`를 먼저 수정하고 pokepedia 저장소 `CLAUDE.md`의 머지 정책을 따른다.
- 기존 퀴즈 코드는 삭제·수정하지 않는다. (예외: 9.7의 우선 출제 — `pickNextPokemon` 확장, 게임 완성 후 별도 PR)

### 9.5 조작 가능성

Unity는 규칙이 클라이언트에 있으므로 결과를 서버에서 검증할 수 없다. 그러나 **배틀 결과가 보상·랭킹에 쓰이지 않으므로** 조작은 본인 경험에만 영향을 준다. 서버 검증 구조는 도입하지 않는다. 승리 보상이나 공식 랭킹을 추가하게 되면 재검토한다.

### 9.7 퀴즈 우선 출제: 배틀 지원 포켓몬이 처음에 등장 [의도 확정, 세부는 게임 완성 후]

- **의도 [확정]:** 퀴즈에서 배틀 지원 포켓몬이 **무조건 처음에 등장**하도록 수정한다. 세부(적용 범위, 방식)는 게임 완성 후 정한다.
- **구현 방향 [권장안]:** `pickNextPokemon`에서 이번 run의 `seen`을 기준으로 **아직 나오지 않은 지원 포켓몬을 먼저** 뽑고, 모두 나온 뒤 일반 풀에서 고른다. DB 변경은 없다. 지원 ID는 Unity `roster.json`의 **빌드 시점 사본**(동기화 스크립트 포함)을 쓰고 퀴즈 서버 경로에서 다른 호스트를 런타임에 호출하지 않는다. Vitest를 추가하고 규칙 변경이므로 `docs/system_design.md` §5를 먼저 수정한 뒤 별도 PR로 진행한다.
- **결정 (2026-10-17, M6):** 배틀을 **아직 안 해 본 사용자의 첫 문제만** 피카츄 실루엣으로 낸다. 맞히면 띠부씰 획득 화면에서 "내 피카츄로 배틀"을 권유한다. 피카츄로 정한 이유: 지금 Demo(피카츄 vs 거북왕)와 그대로 맞아서 매치업·밸런스·연출을 바꿀 필요가 없다. 첫 문제 하나·미체험 사용자만이라 아래 부작용(반복·편중)은 거의 없다. 체험 여부를 어디에 저장할지(브라우저 저장소 / DB)는 M6에서 정한다.
- **부작용 (사용자와 확인한 사항, 처음 안 기준):** 이렇게 하면 모든 run의 첫 6문제가 항상 같은 6마리(순서만 무작위)가 되어 퀴즈가 반복적이고 쉬워지며 해당 스티커가 편중될 수 있다. 세부 결정 때 대안을 검토한다: 사용자가 **아직 갖지 않은** 지원 포켓몬만 우선, 앞 K문제 중 일부만, 가중치 방식 등.

## 10. 웹 배포 인프라

### 10.1 개요 [권장안]

```text
브라우저
 ├─ Pokepedia (Vercel, 기존) ── iframe ──▶ Unity 정적 호스팅 (Cloudflare Pages, 프로젝트 `pokepedia-battle`)
 └─ Supabase (기존) ◀── React만 접근. Unity는 접근하지 않음
```

- **새 서버·DB·게임 서버는 없다.** 필요한 것은 정적 파일 호스팅(CDN)뿐이다. 컬렉션은 기존 Pokepedia 백엔드가 React를 통해 읽어 전달한다.
- 배틀 상태(`BattleState`)는 **브라우저 탭 메모리**에만 존재한다 (클라이언트 측 stateful, 새로고침하면 초기화). 턴제라 서버 쪽 실시간 루프가 없다.
- 브라우저 로컬 저장소(PlayerPrefs)에는 언어·볼륨 같은 설정만 둘 수 있다.
- 화면 비율은 게임보이(약 10:9)를 기준으로 iframe 크기에 맞춰 스케일한다. 입력은 버튼·터치·키보드로 모두 처리 가능하다.

### 10.2 호스팅 선택: **Cloudflare Pages** [확정, 2026-10-17]

- **Pages로 정한 이유 (사용자 결정, 공식 문서 확인):** `pokepedia.dev` DNS는 Vercel이 관리한다(네임서버 `ns1/ns2.vercel-dns.com`, 등록 기관 Name.com). Workers 커스텀 도메인은 DNS가 Cloudflare에 있는 영역에만 붙는다(Cloudflare 문서 "Migrate from Pages to Workers"의 호환표와 Custom Domains 문서: Workers는 "네임서버가 Cloudflare가 아닌 도메인은 지원하지 않는다"). Pages는 외부 DNS에 CNAME 하나로 붙는다. 정적 파일 요청 무료·무제한, 파일당 25 MiB, `_headers` 지원은 둘이 같다. 운영 중인 Pokepedia DNS를 옮기지 않으려고 Pages를 골랐다. 나중에 Pokepedia가 Cloudflare로 옮기면(10.8) Workers로 바꾸기 쉽다(공식 마이그레이션 가이드).
- **주의 (2026-10-17 겪음):** wrangler 4.151은 `wrangler pages project create`를 기본으로 **Worker로 바꿔 만들고 바로 배포**한다. Pages로 만들려면 처음 한 번 `--force`를 붙인다. 이미 Pages 프로젝트가 있으면 이후 `pages deploy`는 Pages로 간다.

**처음 비교한 선택지 (2026-10-16 문서 기준)**

| 선택지 | 평가 | 근거·주의 |
|---|---|---|
| **Cloudflare Workers 정적 자산** | **권장** | 검색 결과 기준 Cloudflare는 신규 프로젝트를 Workers 정적 자산으로 시작하도록 안내하며 Pages는 계속 지원되고 deprecated가 아니다 (공식 문서 원문은 직접 확인하지 못함). 단일 파일 최대 **25 MiB**, 파일 수 Free 20,000개 / Paid 100,000개, 정적 자산 요청은 무료·무제한 |
| Cloudflare Pages | 대안 | 단일 파일 최대 25 MiB, 무료 플랜 파일 수 20,000개, 월 빌드 500회(Git 연동 빌드), `_headers` 규칙 100개까지 |
| Vercel (별도 프로젝트) | 가능, 대안 | CLI 배포 시 업로드 총량 Hobby **100 MB**, Hobby 월 Fast Data Transfer 첫 **100 GB**, 하루 배포 100회. **단일 파일 크기 한도는 문서에서 확인하지 못함.** **Hobby는 비상업적 개인 용도로만 사용 가능** (포트폴리오 용도가 해당하는지 애매하면 지원팀에 문의) |
| GitHub Pages | 비추천 | 커스텀 헤더 불가 → Decompression Fallback 필요(로더 증가, wasm 스트리밍 불가) |
| 개인 서버 | 비추천 | 공개 게임용으로는 가동·보안 운영 부담 |


### 10.3 호스팅 설정

- Unity Web 빌드는 압축 형식에 맞는 `Content-Encoding`(`br` 또는 `gzip`)과 **`.wasm`의 `application/wasm` MIME**이 필요하다 (스트리밍 컴파일). Brotli는 Chrome·Firefox에서 HTTPS에서만 기본 지원한다. 압축을 끄면(Disabled) 파일이 25 MiB 한도를 넘을 수 있으므로 Brotli를 쓴다(M0 PoC 기준 약 9.4MB, 스트리핑 High·LTO를 되돌리기 전 수치).
- 서버에 이미 자동 압축이 있으면 이중 압축이 될 수 있으므로 실제 응답 헤더를 확인한다. **Vercel은 `wasm`·`javascript` MIME을 자동 압축**하므로(문서 기준) Unity 압축을 Disabled로 두는 방법이 있다 (`.data` 같은 `application/octet-stream`은 자동 압축 대상 아님). **첫 로딩 기준값 (2026-10-17, M7 판단용):** 전송량 약 13.4MB(압축 wasm 7.7MB, 데이터 5.6MB, 나머지 0.1MB). 이 PC 회선에서 캐시 없이 받기 약 3.0초, wasm 다운로드가 끝난 뒤 Unity 준비까지 약 0.5초 → 처음 방문 약 3.5초. Fast 4G(9 Mbps) 추정은 다운로드만 약 12초, 모바일 실행 준비를 더하면 약 13~15초(계산값, 실측 아님). 퀴즈에서 넘어오는 흐름(M6)에는 로딩 화면이 필요하고, M7에서 줄일 1순위는 wasm·데이터 크기다.

**Cloudflare Pages 실배포로 확인 (2026-10-17):** `Tools/web/_headers`로 `Build/*.wasm.br`·`*.js.br`·`*.data.br`에 `Content-Encoding: br`과 안쪽 확장자의 Content-Type을 붙이면 그대로 나간다. `Content-Length`가 원본 `.br` 크기와 같아 Cloudflare가 다시 압축하지 않고, 브라우저(크롬 계열)에서 게임이 정상 실행된다. `Build/`는 `Cache-Control: public, max-age=31536000, immutable`, 나머지는 Pages 기본값(`max-age=0, must-revalidate`). Pages `_headers`는 같은 헤더가 여러 규칙에 걸리면 값을 쉼표로 이어 붙이므로 한 헤더는 한 규칙에서만 정한다.
- `Content-Security-Policy: frame-ancestors`로 임베드를 허용할 도메인(Pokepedia, 포트폴리오 허브)만 지정한다. `roster.json`을 Pokepedia가 읽는다면 CORS 헤더를 설정한다.
- 캐시: 로더·`index.html`은 재검증, 해시 파일명(`Name files as hashes`, 구현 시 확인)을 쓰면 빌드 산출물은 장기 캐시.

### 10.4 도메인과 환경

- 서브도메인 **`battle.pokepedia.dev`** [확정, 2026-10-17 연결]. DNS는 Vercel에 그대로 두고 CNAME 하나로 Cloudflare Pages에 붙였다(10.2).
  - **DNS 현황 (공개 조회·Vercel CLI 확인):** 등록 기관 Name.com, 네임서버 `ns1/ns2.vercel-dns.com`, Vercel 계정 `vison901-gmailcoms-projects` 아래에 있다. 기본 레코드는 루트·`*` 와일드카드 ALIAS(Vercel), CAA(`pki.goog`·`sectigo.com`·`letsencrypt.org`)뿐이고 MX·TXT는 없다. `battle` 레코드를 따로 두면 와일드카드보다 우선한다.
  - **연결 절차 (순서 중요, 반대로 하면 522):** ① Cloudflare 대시보드 Workers & Pages → `pokepedia-battle` → Custom domains → Set up a custom domain → `battle.pokepedia.dev` → **My DNS provider → Begin CNAME setup**(왼쪽 "Cloudflare DNS"는 DNS 전체 이전이라 쓰지 않는다). ② Vercel DNS에 `battle CNAME pokepedia-battle.pages.dev` 추가: `npx vercel dns add pokepedia.dev battle CNAME pokepedia-battle.pages.dev`. Vercel MCP는 이 도메인 레코드 조회가 403(팀 범위)이라 CLI로 했다. ③ Cloudflare가 확인하고 인증서를 발급하면 활성화된다. CAA가 Google·Let's Encrypt를 허용해 발급에 문제없다.
  - Pokepedia 프로젝트는 Vercel 팀 henry-dev(Hobby)의 Domains 설정에 `pokepedia.dev`가 Production 도메인으로 연결돼 있다(2026-10-16 사용자 제공 화면).
- Pokepedia에 `NEXT_PUBLIC_BATTLE_URL` 환경변수로 iframe 주소를 둔다 (Prod/Preview 분리 가능, 기존 Zod 환경변수 스키마에 등록).
- Pokepedia의 `next.config.ts`와 `vercel.json`에는 CSP 헤더 설정이 없다 (`src/proxy.ts`는 미확인). iframe 임베드는 추가 설정 없이 될 가능성이 높다.

### 10.5 빌드·배포·CI

- **로컬 Unity Release 빌드 → `python -I Tools/web/deploy.py`** [확정]: `Builds/Web`을 `Builds/deploy`로 복사하고 `_headers`를 넣어 `wrangler pages deploy`로 올린다(`--branch`가 `main`이 아니면 미리보기 배포). 주소는 `https://pokepedia-battle.pages.dev`. Unity CI(GameCI 등)는 라이선스·캐시 설정이 번거로워 이후 검토한다.
- **CI에서는 순수 C# 도메인 테스트만** 실행한다 (GitHub Actions + `dotnet test`). Domain이 UnityEngine을 참조하지 않으므로 별도 테스트 csproj가 Domain 소스를 링크해 Unity 라이선스 없이 매 푸시마다 검증할 수 있다.
- 주의: Unity에서 `record`의 `init` 접근자를 쓰려면 `System.Runtime.CompilerServices.IsExternalInit` 타입을 직접 정의해야 한다 (`Assets/Scripts/Domain/IsExternalInit.cs`).
- 빌드 산출물(`Builds/` 등)은 저장소에 커밋하지 않는다.

### 10.6 모니터링·보안·비용

모니터링은 Cloudflare Web Analytics 정도면 충분하다. 비밀값은 없고, `init`의 `event.origin` 대조와 `frame-ancestors`로 임베드를 제한한다. 비용은 사실상 0원이다.

### 10.7 서버가 필요해지는 시점

승리 보상, 공식 랭킹, 클라우드 세이브, 온라인 PvP를 추가할 때다. 이 경우에도 **새 게임 서버를 만들지 않고 기존 Pokepedia 백엔드를 확장**하는 것을 기본으로 한다. 현재 범위에서는 모두 제외한다.

### 10.8 Pokepedia 호스팅 이전(Vercel → Cloudflare) [범위 밖, 별도 프로젝트로 검토]

Unity를 Cloudflare에 올리는 것이 Pokepedia 이전을 요구하지 않는다(별도 origin + postMessage). 이전은 Next.js 미들웨어(`src/proxy.ts`) 호환과 DB 왕복 지연 등 위험이 커서 Unity 완성 후 별도로 검토한다.

## 15. 개발 에이전트 지침

이 프로젝트의 핵심은 AI가 코드를 생성하는 것이 아니라 **C#과 Unity를 이해하며 만드는 것**이다.

1. 주요 기술 선택에는 이유와 대안을 간단히 설명한다.
2. 새 C#/Unity 개념은 Java와 비교해 설명한다 (7.4 표 참고).
3. Unity 생명주기와 순수 C# 도메인 로직을 구분한다.
4. 규칙은 **테스트를 먼저** 작성한다.
5. 불필요한 프레임워크·인프라를 추가하지 않는다. 과한 추상화를 피한다.
6. 초기부터 웹 빌드 가능성을 유지하고 정기적으로 WebGL 빌드를 확인한다.
7. **Pokepedia 코드·DB는 함부로 수정하지 않는다.** 수정 전 해당 소스, `docs/system_design.md`, pokepedia 저장소 `CLAUDE.md`의 머지 정책을 확인한다. DB 변경이 꼭 필요하면 additive만 허용하고 Prod/Preview가 같은 DB임을 기억한다.
8. 엔진 코드에 포켓몬 이름·스프라이트·문자열을 넣지 않는다. 포켓몬별 코드를 만들지 않는다. **엔진은 로스터 크기를 알지 못한다.**
9. 기능 개발과 에셋 제작을 분리한다. 엔진은 에셋 없이 동작해야 한다.
10. **Showcase 데모도 실제 엔진을 사용해야 한다.** 가짜 전투 로직이나 미리 만든 연출만 재생하지 않는다. Standard와 Showcase를 별도 시스템으로 만들지 않는다.
11. **Vertical Slice 우선**: 콘텐츠를 늘리기 전에 피카츄 vs 거북왕을 먼저 완성한다. 로스터 확장은 데이터 추가 중심으로 한다.
12. **Pokepedia·PokeAPI에 대한 사실을 추측으로 채우지 않는다.** 코드·문서·API를 확인한 뒤 말한다. 외부 제안(GPT 등)의 사실 주장, 특히 기술 이름·규칙·라이선스는 그대로 믿지 않는다.
13. **단순한 사실(버전, 한도, 가격 등)은 에이전트가 웹 검색으로 직접 확인해 문서에 반영한다.** 출처와 확인하지 못한 부분을 함께 적는다.
14. 사용자는 포켓몬 게임 도메인 지식이 약하므로 **규칙·용어는 먼저 설명**하고 추천안과 이유를 제시한 뒤 결정한다. [위임] 항목은 에이전트가 정하되 결과를 문서에 정리한다.
15. 사운드·에셋은 출처와 라이선스를 매니페스트에 기록한다.

### Unity CLI·에이전트 연동 (2026-10-16 확인)

외부 제안(GPT)의 "Unity MCP 도입" 내용을 공식 문서로 검증한 결과다. 출처: [Unity CLI as the replacement for the in-Editor MCP server](https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli).

**확인된 사실**
- 에디터 안 AI Assistant 패키지(`com.unity.ai.assistant`)에 들어 있던 MCP 서버는 deprecated이고, Unity CLI의 `unity mcp`가 대체한다. CLI 자체는 deprecated가 아니다.
- 에이전트가 셸 명령을 실행할 수 있으면 MCP보다 `unity command`·`unity eval`로 에디터를 직접 조작하는 쪽이 빠르고 토큰도 적게 든다고 공식 문서가 안내한다. 따라서 **Claude Code는 MCP가 아니라 CLI 직접 호출을 기본으로 한다.** MCP는 셸을 못 쓰는 환경용 대안이다.
- 연결 절차(공식): CLI 설치 → `unity pipeline install` → (MCP가 필요하면) `unity mcp configure <client>` → `unity skill install <agent-name>`.
- 실행 중인 에디터 조작은 Unity 6.0 LTS 이상 필요. 현재 6000.3.26f1은 해당된다. CLI는 무료이며 Unity AI 구독과 무관하다. 로컬 연결만 받는다(localhost).
- 에디터 없이 헤드리스 빌드·테스트 실행도 가능하다. 이 저장소는 이미 `unity test . --mode EditMode`를 쓰고 있고, 로컬에 CLI `1.0.0-beta.13`이 설치돼 있다.
- 아직 `unity pipeline install`은 하지 않았다(`Packages/manifest.json`에 파이프라인 패키지 없음). 설치하면 패키지가 추가되므로 PR로 변경을 확인한다.

**확인하지 못한 것 (그대로 믿지 말 것)**
- GPT가 적은 `winget install Unity.CLI` 패키지명과 `codex plugin marketplace add Unity-Technologies/unity-agent-plugin` 명령. 설치는 공식 Install Unity CLI 절차를 따른다.
- `unity skill install`에서 쓸 에이전트 이름(`--help`로 확인).
- `unity command`·`unity eval`이 실행 중인 에디터를 반드시 필요로 하는지. 문서의 "running Editor" 표현에서 추정한 것이다.
- GPT가 전한 CoreCLR 로드맵(Unity 7.0에서 CoreCLR 에디터 도입 등). 공식 확인 전이다. 어느 쪽이든 WebGL 빌드는 IL2CPP라 6.3 LTS 유지 결정에는 영향이 없다고 본다.

**운영 주의**
- 에디터 단일 점유와 병렬 작업 규칙은 [CLAUDE.md](../CLAUDE.md)를 따른다.
- `unity eval`은 에디터에서 임의 C#을 실행할 수 있다. 권한 허용 목록에는 필요한 명령만 넣는다.
